# Incident Report — Site Down, 2026-07-06

## What happened

The site (sourovdeb.com) went down with a "critical error" on all front-end
pages (homepage, posts) while wp-admin login and the REST API kept working.
That split symptom was the key clue.

## Root cause

`wp-content/themes/Webpage design/sourov-theme_a/functions.php` declares
`namespace Sourov;` at the top of the file. Near the bottom it defines a
function and registers it as a hook using a **bare string**:

```php
function custom_homepage_query($query) { ... }
add_action('pre_get_posts', 'custom_homepage_query');
```

Inside a namespace, that function is actually named `Sourov\custom_homepage_query`
— but the string `'custom_homepage_query'` passed to `add_action()` tells
WordPress to call a **global** function of that name, which doesn't exist.
`pre_get_posts` fires on every front-end page that runs a main query (home,
single posts, archives) but not on wp-login, wp-admin dashboard load, or
custom REST routes — which is exactly why those kept working while
everything else 500'd.

**Fix:** one line, `'custom_homepage_query'` → `__NAMESPACE__ . '\\custom_homepage_query'`,
so the hook resolves to the real namespaced function. No functionality was
removed — the homepage sort-order behavior is unchanged.

## Contributing mess (not the direct cause, but made diagnosis harder)

- A second, already-fixed copy of the "Sourov AI Controller" plugin existed
  on disk as `sourov-ai-controller-d.php` (v1.3, changelog: *"removed
  undefined `sourov_enforce_pillars()` call"* — literally the fix for an
  earlier fatal). But WordPress's `active_plugins` option still pointed at
  the old filename `sourov-ai-controller.php`, which had been deleted/renamed
  away. The REST API kept responding, but with **stale v1.0 behavior served
  from LiteSpeed's page cache** — not the real, fixed v1.3 code. This is
  reconciled now (see "What was removed / fixed" below).
- Several one-off "fix" and "diagnostic" PHP files were dropped directly
  into `wp-content/plugins/` as loose files (not folders) during rapid
  iteration, several edited today during the incident itself. Loose files
  in that directory are silently treated as single-file plugins by
  WordPress the moment they're marked active — easy to lose track of which
  ones are live.
- `mu-plugins/calm-cron.php` threw a fatal (`Path cannot be empty`), but
  **only under WP-CLI**, not on web requests — a red herring that looked
  scarier than it was. The `mu-plugins` directory has since been removed
  entirely (renamed away during troubleshooting), which also removed the
  duplicate `sourov_enforce_pillars()` declaration that caused an earlier,
  separate fatal.

## What was removed / fixed (2026-07-06, live site)

- Fixed: `functions.php` namespace/hook bug (root cause, above).
- Fixed: restored the real, patched v1.3 controller under its expected
  filename `sourov-ai-controller.php`; removed the orphaned duplicate
  `sourov-ai-controller-d.php`.
- Removed: `aicu-command-center.php` (already-disabled, caused a
  `count(): null` fatal on the wp-admin dashboard widget) — file deleted,
  and its stale entry purged from the `active_plugins` option via
  WordPress's own `validate_active_plugins()`.
- Removed: `crawl-page.php` — an unauthenticated URL-fetch utility
  (OpenClaw crawler) sitting directly in the public `wp-content/plugins/`
  folder. It happened to be inert as deployed (its fetch logic only runs
  under CLI), but an unauthenticated fetch endpoint has no reason to live
  in a public web folder — see "future AI" rules below.
- Removed: `hello.php` (WordPress's default "Hello Dolly" sample plugin —
  inactive, harmless, just clutter).
- Removed: `akismet.4670/` — an orphaned duplicate directory left behind by
  an interrupted plugin update.
